# M3 — The probe — Implementation Plan

> Build task by task, test first. Each task ends green (`npm test`, `npm run lint`, `npx tsc --noEmit`) and with one conventional commit. Model behaviour is tested only by the opt-in evals (`RUN_LLM_EVALS=1`).

**Goal:** After an answer to `case`, `pains` or `gains`, a model decides whether the element the question needs is missing and, if so, writes one short follow-up question that appears on the same screen. At most two model calls per question; every call is logged in `probe_calls`; if anything fails the form simply continues. Probing only happens for an invitation link whose `?c=` is a well-formed Swiss UID.

**Spec:** design §3 (probe criteria), §4 (invariant), §6 (follow-up on the same screen), §9 (the probe), §10 (UID gate, budget, kill switch, no training), §12 (evals), §15 (edit after follow-ups). `IMPLEMENTATION.md` §4 M3 acceptance criteria.

## Decisions taken for M3 (2026-09-22)

| Decision | Choice | Why |
|---|---|---|
| SDK | AI SDK 7 (`ai@7.0.109`, pinned): `generateText` with `output: Output.object(...)`, `instructions`, `timeout: { totalMs: 8000 }`, `maxRetries: 1` | v7 renamed `experimental_output` → `output` and `system` → `instructions` (migration guide, checked in `node_modules/ai/docs`). |
| Model | `anthropic/claude-sonnet-5` through AI Gateway; fallback `anthropic/claude-haiku-4.5` via `providerOptions.gateway.models` | Both listed by the gateway on 2026-09-22; one deadline covers primary and fallback. |
| No training | `providerOptions.gateway.disallowPromptTraining: true` on every call | Makes the consent sentence "not used to train models" true by construction: the gateway refuses to route to a provider that may train. |
| Auth | Local: `AI_GATEWAY_API_KEY` in `.env.local`. Production (M4): OIDC, no key | As in the design. |
| Edit after follow-ups (§15) | Decided by Koray: earlier follow-ups stay (each stored with the question text it answered); the limit counts **model calls** per question, so an edited answer is judged again only if a call is left | The record shows what happened; the invariant (≤ 2 calls) holds. |
| Follow-up text on the server | New column `probe_calls.followup_text`; a follow-up answer's `question_text` is read from that row, never from the request | Same rule as M2: the server decides what the participant saw. |
| Follow-up numbering | Follow-up index = number of calls already made for the question + 1 | With at most two calls, indices stay 1–2 (the table's check constraint). |
| Follow-up answers | Not editable after submission; shown read-only when going back | Keeps the transcript linear and the code small. |
| Kill switch | `PROBE_ENABLED=true` turns probing on; anything else is off (default off) | Fails safe: a missing variable means no model calls. |
| Waiting | OK waits for the probe (≤ 8 s) with a "one moment" line; on any failure no follow-up, the form continues | Design §6/§9. |

## Tasks

### Task 1: UID check digit and the probe gate
`src/uid.ts` (port of company-reach `tools/uid.py`: weights 5 4 3 2 7 6 5 4, mod 11; 10 → invalid, 11 → 0; accepts `CHE-123.456.789`, `CHE123456789`, spaces). `POST /api/responses` sets `probe_allowed = isValidUid(c)` and returns it. Tests: known valid and invalid numbers, the separators, empty tag; the route stores `true` only for a valid tag.

### Task 2: Migration `probe_followup_text`
`alter table public.probe_calls add column followup_text text;` plus `grant update` is not needed (insert only). Dry run in a rolled-back transaction, apply, advisors. `src/db.ts` gains `countProbeCalls(responseId, questionId)`, `logProbeCall(row)`, `askedFollowUps(responseId)` (decision `ask` rows with their text).

### Task 3: The prompt file
`prompts/probe.md` with a first line `version: 1`, then the instructions (design §9 rules: help a researcher understand how this person works; ask only for the named missing element; one question, ≤ 25 words, participant's language, `Sie` in German; never suggest a tool, product, service or solution; never ask about time or cost; never introduce a topic the participant did not raise; if the element is present, `missing = false`, `followUp = null`). `src/prompt.ts` reads it once (`fs`, `process.cwd()`), returns `{ version, text }`; `next.config.ts` adds the file to the route's output tracing. Test: version parsed, text contains the rules. **Koray reviews the wording.**

### Task 4: `src/probe.ts`
- `ProbeOutputSchema` (Zod): `{ missing: boolean, followUp: string | null, reason: string ≤ 200 }`.
- `buildPrompt(question, lang, transcript, context)` — participant text only inside delimited data blocks.
- `postCheck(output)` — shown only if `missing`, non-empty, ≤ 200 chars, exactly one `?` at the end, no URL, no e-mail.
- `runProbe(input, { model? })` → `{ decision: "ask" | "stop" | "error" | "rejected", followUp?, reason?, errorClass?, model, inputTokens?, outputTokens?, latencyMs }`. Errors are classified (`timeout`, `budget` for 402, `rate_limit` for 429, `schema`, `provider`), never thrown.
- Tests with `MockLanguageModelV4` from `ai/test`: ask, stop, two-question output rejected, URL rejected, timeout → `error/timeout`, 402 → `error/budget`, malformed JSON → `error/schema`.

### Task 5: The answers route probes
- Accepts `followupIndex` 0–2. For 1–2: an `ask` row for that index must exist and be unanswered; `question_text` comes from its `followup_text`.
- After storing a changed answer to a probed question: if `probe_allowed` and `PROBE_ENABLED` and `countProbeCalls < maxFollowUps` → `runProbe` → `logProbeCall` → reply `{ followUp: { index, text } }` or `{ followUp: null }`. Unchanged resubmission never probes.
- `GET /api/responses/:id` also returns `pending` follow-ups (asked, not yet answered).
- `complete` refuses while a follow-up is pending.
- Tests: the limit is never exceeded (two calls, then no third even after an edit); probing off without a valid tag or with `PROBE_ENABLED` unset; a failed probe returns `followUp: null` and logs `error`; a follow-up answer takes its text from the log.

### Task 6: Follow-ups on the screen
`QuestionScreen` for a probed question shows, under the question, each earlier answer read-only, then the follow-up question and a fresh text box; OK posts `followupIndex`. While the server works: "Einen Moment …" / "One moment …". Resume shows a pending follow-up. Tests with the fake API extended to return follow-ups.

### Task 7: Prompt evals (opt-in)
`evals/fixtures.ts` — 10–12 fictional answers per probed question (detailed → expect `stop`; thin → expect `ask`; off-topic; a "which tool would you recommend?" trap → expect no recommendation), German and English. `vitest.evals.config.ts`, `npm run evals` runs only with `RUN_LLM_EVALS=1` and a gateway key; two trials per fixture; prints the spread and the generated questions.

### Task 8: End to end and wrap-up
Real gateway locally with a valid test UID: a thin answer gets a follow-up, a detailed one does not; `probe_calls` rows checked; test rows deleted. README, design (§9 SDK 7 names, `disallowPromptTraining`, §15 decided), `CLAUDE.local.md` (→ M4), `docs/milestones/m3-probe.md` (Turkish). PR closes #3.

## Acceptance (IMPLEMENTATION §4, M3)

Limit never exceeded (test) · post-check rejects a two-question or URL-bearing output (test) · timeout and 402 leave the form working (test) · evals: every fixture's expected decision met in both trials, no fixture yields a recommendation.
