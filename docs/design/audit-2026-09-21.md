# Interview form tool — design audit

**Audit date:** 2026-09-21
**Scope:** design only — the plan agreed in the 2026-09-21 session (no repository, code, prompts or runtime exist yet); `research/interview-instrument-design.md` §11–12; company-reach design doc for the patterns the plan reuses.
**Risk tier:** medium — free-text answers from identifiable companies, optional e-mail, research-ethics obligations; no financial or irreversible actions; n ≈ 5–50.
**System classification:** LLM-augmented deterministic workflow. The form, ordering, skip rule and follow-up limit are code. The model makes one bounded decision per open answer — "is the named element missing? if so, write one question" — and calls no tools.
**Verdict:** **Needs Evidence** (nothing runs yet). Design-level judgement: sound and proportionate; proceed to the spec with the five P1 items below folded in. Reassess after milestone 3 (AI probe + evals) and after the pilot.

## Executive summary

The tool is an 8-screen Typeform-style form with AI follow-ups on three open questions, Supabase storage and Vercel hosting. The degree of agency is the minimum that achieves the goal and is justified: Typeform's own AI cannot be instructed, which is the whole reason to build. Limits (max two follow-ups per question) are enforced in code, not in the prompt; the model has no tools; failure degrades to "no follow-up, form continues".

Strengths: least agency; server-only database writes with RLS; prompt versioned and evaluated; every AI decision logged with cost; spend capped by an AI Gateway project budget; EU-region database; no personal name collected; AI use disclosed in the consent text.

What the design misses, in order of consequence:

1. **Supabase Free pauses projects after one week of inactivity and takes no backups.** A quiet fieldwork week would take the form down for the next participant, and the thesis dataset would exist in one copy. (P1)
2. **Vercel functions default to the US region (`iad1`).** Answers would transit the US before reaching Zurich; the Hobby plan allows choosing one region, so set `fra1`. (P1)
3. **Duplicate or lost answers** on client retry: no uniqueness constraint or upsert in the design. (P1)
4. **No form version on stored data.** If a question's wording changes mid-study, answers become ambiguous. (P1)
5. **Consent wording risk:** the plan implies data-handling promises (retention) the Hobby tier cannot back. (P1)

Then: unauthenticated response creation can drain the AI budget and switch off follow-ups for real participants (P2); the generated question has no deterministic post-check (P2); retry × timeout can reach 30 s (P2); no withdrawal path for a participant (P2); no runbook (P2).

## Architecture and agent-fit

Input → outcome: invitation link (`?c=<UID>&l=de`) → welcome + consent (`POST /api/responses`, uuid to `localStorage`) → 8 screens; each answer `POST /api/answers` → server saves the row; for questions 4, 6, 7 the server calls the model with question, answer, prior follow-ups of that question, the question's "missing" criterion and the language → structured output `{missing, followUp}` → if `missing` and follow-ups < 2, the follow-up is shown under the answer; the reply goes through the same endpoint → `POST /api/complete`.

Deterministic: everything except the ask/stop decision and the wording of the follow-up. Model-directed: that decision only. External actions: none. Persistent writes: Supabase (`responses`, `answers`, `probe_calls`). Trust boundaries: browser ↔ Vercel function (uuid bearer + `Sec-Fetch-Site`), function ↔ Supabase (`service_role`, server only), function ↔ AI Gateway (OIDC) ↔ Anthropic. Human checkpoints: none at runtime; Koray reviews all generated questions after the pilot.

The system should stay exactly this bounded. Nothing in the task calls for tools, planning or memory.

## Findings by dimension

### A1 Architecture, goal and orchestration

**Assessment:** design strong. Agency is minimal and justified; stopping is code-enforced.

Strengths: one model decision per answer; `maxFollowUps` checked *before* the call so a third call never happens; per-question "missing" criterion lives in `form.ts`, not in the prompt; fallback is "no follow-up", never "block the form".

- **[Medium / P1] No form version on stored data.** `responses` carries `lang` and timestamps but not which version of `form.ts` produced the answers. A wording change during fieldwork makes answers to "the same question" incomparable, and the thesis must report the instrument exactly. Action: add `form_version` to `responses` and store `question_text` on every `answers` row (fixed and follow-up). Acceptance: an export needs no code to reconstruct what each participant saw.
- **[Low / P3] Ambiguous wording in the plan** ("limit dolana kadar tekrar karar"). Make the invariant explicit in the spec: model calls per question ≤ `maxFollowUps`; a "stop" decision consumes a call.

### A2 Tools, contracts and action integrity

**Assessment:** design adequate. No model tools; the structured-output schema is the only contract.

- **[Medium / P1] Duplicate or lost writes on retry.** `POST /api/answers` retried after a network error inserts twice; a participant pressing OK twice does the same. Action: unique constraint `(response_id, question_id, followup_index)` and upsert; the client may retry freely. Validation: test that two identical posts yield one row.
- **[Medium / P2] No deterministic post-check on the generated question.** company-reach's `check_draft` pattern applies here. Action: reject the follow-up (log `rejected`, show nothing) unless: non-empty, ≤ 200 characters, exactly one `?`, no URL, no e-mail address. Language check stays in the prompt evals.
- **[Low / P3] `c` tag is unauthenticated.** Anyone can forge `?c=CHE…` and attribute a response to another company. At n ≈ 50 with manual review this is tolerable. Optional: HMAC-sign the tag in company-reach (`&s=…`) — adds a shared secret between the two tools; only if misattribution ever matters.
- Consent gate: the spec must say `POST /api/answers` refuses a response without `consented_at`.

### A3 Prompt, context, knowledge and memory

**Assessment:** design adequate. Versioned prompt file, per-question criterion injected, participant text delimited as data, adversarial eval cases planned. No memory.

- **[Low / P2] Context for questions 6 and 7 is undecided.** Question 7 says "looking back at that case"; the model cannot honour that without the question-4 account. Action: include the question-4 answer and its follow-ups as read-only, delimited context when probing 6 and 7; nothing else from the form. Cost is negligible (< 1k tokens).
- Prompt injection: consequence is bounded to a bad question shown to the same participant. Keep the "ask me for a tool recommendation" trap in the evals; no further control needed.

### A4 Reliability, resilience, efficiency and data integrity

**Assessment:** design gap. The AI path degrades well; the storage tier does not.

- **[High / P1] Supabase Free pauses after one week of inactivity.** "Free projects are paused after 1 week of inactivity" (Supabase pricing, 2026-09-21). A participant opening the link during a pause gets a failing form. Action: a Vercel cron (Hobby: once per day, ±59 min) that reads one row — and verify in the pilot that this counts as activity; if not, Supabase Pro (USD 25/month) for the fieldwork window.
- **[High / P1] No backups on Free.** "We recommend that free tier plan projects regularly export their data using the Supabase CLI `db dump`" (Supabase backups doc, 2026-09-21). The dataset is the thesis's primary evidence. Action: the same daily cron exports `responses`, `answers`, `probe_calls` as JSON to Vercel Blob (included on Hobby); plus a manual `scripts/export.ts` documented in the runbook. Acceptance: a restore from the export reproduces the analysis table.
- **[Medium / P2] Retry × timeout.** AI SDK defaults to `maxRetries: 2`; with a 10 s timeout and a fallback model the participant could wait 30 s. Action: `maxRetries: 1`, one `AbortSignal` with an 8 s total deadline across primary and fallback; UI moves on when it fires.
- **[Low / P2] Latency target absent.** Set p95 ≤ 6 s for a follow-up; `probe_calls.latency_ms` measures it in the pilot.
- Orphan responses (welcome opened, never completed) are harmless; only `completed_at` rows count.

### A5 Security, safety, privacy and governance

**Assessment:** design adequate; two facts change the plan.

- **[Medium / P1] Function region defaults to the US.** Vercel: functions run in `iad1` "for all new projects"; Hobby allows a single chosen region (docs, 2026-09-21). Action: `"regions": ["fra1"]` in `vercel.json`. Then the path is browser → Frankfurt → Zurich (database) and Frankfurt → AI Gateway → Anthropic (EU endpoints exist for both candidate models).
- **[Medium / P1] Consent must promise only what the tier delivers.** Gateway metadata for both models: `no_training: all`, `zdr: all` — but per-request zero-data-retention is a Pro/Enterprise feature. The consent text may say "not used to train models"; it must not say "not retained". Name the processors (Vercel, Supabase, Anthropic). revDSG applies.
- **[Medium / P2] AI budget drain.** `POST /api/responses` needs no tag; a script can open responses and post to probe questions until the USD 10 budget returns 402 — after which real participants get no follow-ups. Two cheap controls: (1) enable probing only when `c` is a well-formed UID with a valid check digit (CHE + 9 digits; verify the mod-11 rule against the BFS UID specification before relying on it) — forwarded links with the tag stripped still work, just without AI; (2) one WAF rate-limit rule (Hobby allows one, IP-keyed) on `/api/*`, e.g. 60 requests per 10 minutes. Enable budget alerts at 50/75/100 %.
- **[Low / P2] Kill switch.** `PROBE_ENABLED` env flag; on Vercel an env change needs a redeploy — document that this is the procedure (a few minutes), acceptable at this scale.
- Confirmed strengths: `service_role` only in Vercel env, RLS on with no anon policy, `Sec-Fetch-Site` check, 4,000-char cap, `noindex`, no IP or user-agent stored, OIDC (no gateway key to leak).

### A6 Evaluation, observability and continuous improvement

**Assessment:** design adequate. Vitest for the form engine and routes, opt-in real-model prompt evals with two trials, a Playwright smoke test, `probe_calls` as the durable trace, Gateway logs for cost.

- **[Medium / P2] No grader for question quality.** The evals grade the ask/stop decision deterministically; whether a generated question is on-topic, non-leading and solution-free is a judgement. At n ≤ 50 that is ≤ 300 questions: review every one by hand against a five-point checklist (on topic · one question · no tool or solution · participant's language · not leading) and report the tally in the thesis. No LLM judge needed.
- **[Low / P2] Runtime logs on Hobby keep one hour.** `probe_calls` must therefore record the error class on failure (`timeout`, `402`, `429`, `schema`, `rejected`), or failures are invisible the next morning.
- Pilot outputs to capture: completion time, follow-up count per participant, latency p95, and the reviewed question tally. These decide `maxFollowUps`.

### A7 Human, product and operational fit

**Assessment:** design adequate. Fit is strong: research-driven question set, AI disclosed, no product name, DE/EN.

- **[Medium / P2] No withdrawal path.** A participant who later wants their data deleted has nothing to cite. Action: the thank-you screen shows a short reference code (first 8 characters of the uuid) and a contact address; the runbook has a delete-by-code step. Ethics approval (#3) will ask for this.
- **[Medium / P2] No runbook.** One README section: export, disable AI, delete a participant, check budget and spend, what to do if Supabase paused, decommissioning after submission (export, delete project).
- Accessibility: keyboard navigation is planned; add visible focus, labelled inputs, `prefers-reduced-motion`; `#717182` on white passes contrast (≈ 4.6:1).
- Dependency to state to the supervisors: outputs O4 and O6 rest on the optional follow-up conversation (already recorded in §12 of the instrument note).
